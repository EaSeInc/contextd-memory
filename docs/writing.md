# Запись: дедупликация, мусор, приоритеты

Память портится не от нехватки записей, а от их количества. Индексатор, который
гонит историю чатов в базу каждый час, за сутки делает тысячи записей — и без
фильтров поиск тонет в пересказах одного и того же разговора.

`_remember_one()` — четыре барьера до `INSERT`.

## 1. Мусор

```python
def _garbage(text, kind):
    resid = " ".join(_TOOL_RX.sub(" ", text).split())
    if not resid:
        return "пусто"
    if len(resid) < 80 and _TOOL_RX.search(text):
        return "только вызовы тулов"
    if len(resid) < 40 and kind not in ("fact", "constraint"):
        return "слишком коротко"
    if len(resid) < 300 and any(m in resid.lower() for m in _INCOMPLETE):
        return "оборванный ход"
    return ""
```

Причина возвращается клиенту в `reason`, запись не создаётся. Порог в 80 символов
для «только вызовы тулов» нужен, чтобы не выкинуть ответ, где тулы — часть работы:
мусор — это когда кроме вызовов ничего нет.

## 2. Нормализованный ключ

Один и тот же текст приходит как `U: текст`, `> текст`, с вкраплениями
`[ran tool: …]`, в другом регистре и с ё/е. Без нормализации это четыре разных
записи.

```python
def _nkey(text):
    t = _TOOL_RX.sub(" ", text)              # вызовы тулов
    t = _ROLE_RX.sub("", t).lower().replace("ё", "е")
    bare = _NONWORD.sub("", t)               # только буквы и цифры
    if not bare:                             # ничего не осталось
        return "e" + sha1(text)[:23]         # уникальный ключ
    return sha1(bare)[:24]
```

Тонкость: если после чистки не осталось ни слова, ключ **не должен** быть общим.
Иначе весь мусор схлопывается в одну группу «дублей», и `/dedupe` сносит восемь
записей из девяти как копии. Префикс `e` + хеш от полного текста гарантирует
уникальность.

Найденный ключ → `UPDATE updated_at`, `tags`, `pinned=max(...)`, `priority=max(...)`
и ответ `action: "duplicate"`. Время и теги освежаются, текст не дублируется.

## 3. Смысловой почти-дубль

Только для `fact`, `decision`, `constraint`, `settings` — у `skill` и `chat`
«похожий текст» означает нарезку файла на чанки или перекрытие окон индексатора,
и склейка там теряет содержимое.

Алгоритм:

1. Основы слов (`_stems`), минимум 6 штук — иначе кандидатов не искать.
2. Кандидаты через FTS по основам (top 8), тот же `kind`.
3. Jaccard основ ≥ 0.9 → merge в более длинный текст, теги объединяются.

Почему Jaccard, а не containment: короткая запись целиком входит в длинную, и
`∩/min` даёт 1.0 при Jaccard 0.1 — это не дубль, это «упоминание внутри».

Порог 0.9 подобран на боевой базе: пар с Jaccard ≥ 0.8 у `fact`/`constraint`/
`settings` почти нет (0–1 на несколько тысяч), а у `skill` — 182, у `chat` — 23.
То есть порог 0.9 ничего живого не склеивает, а 0.72 (порог выдачи) склеил бы.

## 4. Уникальный индекс

Последний барьер — `UNIQUE(topic, kind, text)` с `ON CONFLICT DO UPDATE`: теги,
`source`, `pinned`, `priority`, `updated_at` обновляются, дубль не создаётся.
Возвращается `action: "updated"` (в отличие от `inserted`, где строка новая —
это видно по `created_at = ts`).

## Приоритеты

```python
PRIORITY_BY_KIND = {
    "constraint": 75, "decision": 70, "settings": 65,
    "fact": 60, "skill": 40, "chat": 30,
}
```

- `pinned=True` → 100.
- явное поле `priority` (1–100) перебивает всё.
- при повторной записи приоритет только повышается (`max(priority, ?)`), никогда
  не понижается автоматически: иначе индексатор, перезалив чанк, сбрасывал бы
  вручную поднятый приоритет.

Смысл градации — в бюджете. Когда в 400 токенов не влезает всё, первым вылетает
`chat` (30), последним — `constraint` (75). Это не «важность вообще», а «что
дешевле потерять в тесном окне».

## Что писать и что не писать

Хорошая запись:

```
PETG печатать: сопло 240, стол 80, обдув 50 %        — settings, тема print/petg
PF450 тянет одну карту ~180 Вт, две — нет            — constraint, тема infra/power
Мост Fusion MCP: http://127.0.0.1:27182/mcp          — settings, тема fusion
```

Плохая запись:

```
Мы долго обсуждали, как лучше печатать PETG, и пришли к выводу,
что 240 градусов выглядит разумно, но надо проверить на практике…
```

Правила:

1. Одна запись = одна мысль. 1–2 предложения, до ~200 символов.
2. Запись должна быть понятна **без** контекста разговора: без «это», «там»,
   «как мы говорили». Она всплывёт в чужом контексте.
3. Числа, пути, порты, имена — доподлинно. Не «примерно 240», а «240».
4. Не писать то, что меняется через день (статус задачи, «сейчас проверяю»).
5. Секреты не писать вообще — только указатель на файл, где лежит пароль.

## Секреты

В самом `contextd.py` фильтра значений нет — вычистка живёт на стороне
индексаторов (`skills_index`, `sessions_index`, `ctxagent._redact`), потому что
только они тянут тексты, где секрет может оказаться.

Это ограничение стоит признавать: `curl -X POST /remember -d '{"text":"пароль
admin: hunter2"}'` ляжет в базу как есть. Правило «секрет — в файл, в память —
указатель на файл» держится на дисциплине пишущего, а не на сервере.

Индексатор истории чатов режет по регулярке:

```python
SECRET_RX = re.compile(
    r"(?i)(password|passwd|пароль|token|токен|secret|api[_-]?key|authorization|bearer)"
    r"(\s*[:=]\s*|\s+)(\S{6,})")
```

Тонкость, на которой легко обжечься: регулярка ловит значение только когда
ключевое слово стоит **вплотную**. Сообщение, состоящее из одного пароля, проходит
фильтр целиком. Поэтому пароль, отправленный в чат, реально доезжает до базы через
индексатор — лечится добавлением правила «строка без пробелов ≥ 12 символов с
цифрами и спецсимволами».

## Уборка накопленного

`POST /dedupe?apply=false` — посчитать, `apply=true` — удалить. Группы строятся по
`nkey`, из группы остаётся самая длинная запись (при равенстве — самая старая,
`pinned` в приоритете). `garbage=true` дополнительно сносит то, что не прошло бы
`_garbage` сегодня.

На боевой базе после месяцев работы индексаторов: `groups: 0, would_delete: 0` —
новые барьеры держат, уборка нужна была только для того, что накопилось до них.

Мутация необратимая: бэкап до `apply=true`, и сначала `dry_run` с глазами на
`sample`.
