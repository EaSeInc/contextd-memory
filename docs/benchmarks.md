# Замеры

Все цифры ниже получены на одной боевой базе 16.11.2026: 9 212 фактов, 120 тем,
`facts` 5 870 чанков скилов / 3 124 чанка чатов / 218 ручных записей
(`fact` 85, `settings` 64, `constraint` 35, `decision` 34), средняя длина
615 символов, база 177 МБ.

Железо: i3-4170T (2 ядра / 4 потока), 8 ГБ RAM, RX 550 4 ГБ; эмбеддинги —
`bge-m3-q8.gguf` на CPU, сервис — uvicorn, один воркер.

## Методика

Главная ошибка при оценке памяти — мерить «сколько записей пришло». Пять записей в
выдаче выглядят одинаково хорошо и когда это пять разных фактов, и когда это пять
кусков одного разговора. Поэтому:

1. Задать **gold-набор**: запрос → подстрока, которая обязана появиться в выдаче.
   Подстрока уникальна для нужного факта (`jaccard`, `pf450`, `8085`).
2. Считать долю запросов с попаданием и MRR (1/позиция нужной записи).
3. Отдельно задать **посторонние** запросы — они должны молчать (для хука) или
   отдавать низкий скор (для `/recall`).
4. Латентность — по тем же вызовам, warm (после первого).

Скрипт: `bench/recall_bench.py`, параметры через аргументы. Набор из 12 кейсов —
**±1 кейс это 8 процентных пунктов**, поэтому таблицы читать как «порядок», а не
как «качество 83 %». MRR между прогонами плавает на ±0.02: индексаторы в это время
перезаливают чанки, и база под замерами меняется.

## `/recall`, gold-набор (12 запросов, limit 5, budget 400)

| Конфигурация | Попаданий | MRR | Медиана, мс | p90, мс |
|---|---|---|---|---|
| по умолчанию (`fts_w=0.3`, `vec_w=1.0`) | 10/12 | 0.729 | 159 | 166 |
| равные веса (`1.0 / 1.0`) | 9/12 | 0.694 | 147 | 175 |
| только FTS (`vec_w=0`) | 8/12 | 0.472 | 159 | 176 |
| только вектор (`fts_w=0`) | 11/12 | 0.701 | 159 | 166 |

Что из этого следует честно:

- **Лексика одна не тянет** — 8/12 и MRR 0.47. Перефраз («насос по памяти» вместо
  «эмбеддер») её убивает.
- **Вектор один тянет почти всё** — 11/12. Это не значит «FTS не нужен»: на
  запросах с кодами железа (`PF450`, `p104`) вектор путает близкие шифры, а
  лексика попадает точно. Набор мал, разница в один кейс — шум.
- **Равные веса хуже дефолта** — согласуется с прежними замерами (там же: `vec_w=0.5`
  ронял семантику вдвое).
- **Промахи дефолта** — там, где запрос и факт не делят ни одной основы: «дедупликация
  памяти» против записи про `jaccard`, «камера принтера стрим» против `ustreamer`.
  Это ограничение лексического канала, а не слияния.

## Посторонние запросы

```
рецепт борща с говядиной   → 4 записи, топ-скор 0.016
погода в лионе завтра      → 4 записи, топ-скор 0.016
котировки акций теслы      → 4 записи, топ-скор 0.016
```

`/recall` **всегда** что-то отдаёт: если ни один канал не нашёл, срабатывает
fallback «последние записи». Скор при этом минимальный (0.016) — ровно поэтому
хук фильтрует по основам слов, а не по скору.

## Хук в промпт (15 прогонов `/recall_hook`)

| Метрика | Значение |
|---|---|
| Целевых запросов с нужным фактом в блоке | 9/12 |
| Посторонних запросов с молчанием | 3/3 |
| Средний размер блока | 466 символов (~145 токенов) |
| Средняя задержка | 205 мс (первый вызов 769 мс) |
| Строк памяти в блоке | 0–4, типично 2–3 |

Промахи: «дедупликация памяти» (в блоке только одна строка, не та),
«как поднять обход через VPS» (пришли записи, но без нужного слова),
«камера принтера стрим» (пустой блок — нет пересечения основ).
Это ровно та цена, которую платит фильтр по основам за 3/3 молчания на мусоре.

## Латентность по эндпоинтам

| Вызов | Медиана | Заметки |
|---|---|---|
| `/health` | ~2 мс | без токена, без эмбеддера |
| `/recall` (warm) | 159 мс | из них ~140 мс — вызов bge-m3 на CPU |
| `/recall` (первый) | 686 мс | прогрев модели |
| `/recall_hook` | 205 мс | recall + фильтр по основам |
| `/remember` | 130–700 мс | зависит от того, нужен ли эмбеддинг |
| `/dedupe?apply=false` | ~1.5 с | полный скан 9 212 записей |

Хук стоит на каждом ходу, поэтому 200 мс — верхняя граница комфорта при
4-секундном таймауте клиента. Если эмбеддер недоступен, `/recall` падает до ~15 мс
(только FTS) — быстрее и хуже.

## Прежние замеры, которые определили дефолты

Они делались на этой же базе меньшего размера и остались в силе:

- **Реранк**: MRR 0.771 без него, 0.729 с ним, +1.5 с на запрос → выключен.
- **Recency-буст**: MRR не меняется (0.771 и там, и там) → выключен.
- **Штраф чату** (`chat_w=0.6`): MRR 0.771 → 0.729, шум не убирает → выключен.
- **`max_chars` / `per_topic`**: сетка 4×3 на 12 запросах дала 12/12 при
  `max_chars=250`, 11/12 при 400 и 600; `per_topic=2` и `3` равны по покрытию, у 2
  разнообразие тем выше (3.2 против 3.0) → дефолт 250/2.
- **Построчная нарезка блока хука**: 11/12 при `per_line = max_chars//limit` против
  9/12 при подсчёте по сумме строк.

## Как воспроизвести

```bash
export CONTEXTD_URL=http://127.0.0.1:8090
export CONTEXTD_TOKEN=...
python bench/recall_bench.py --gold bench/gold-example.json --compare
```

`--compare` прогоняет четыре весовые конфигурации и печатает таблицу. Gold-файл —
JSON `[{"q": "...", "needle": "..."}, ...]`; свои кейсы — свои ожидаемые подстроки,
взятые из реальных записей вашей базы.
