# Поиск: как выбирается, что попадёт в промпт

Запрос `/recall` проходит четыре независимых ограничителя. Полезно понимать, где
именно теряется нужная запись — «поиск не находит» почти всегда означает не матч,
а позднюю стадию.

```
q ──► FTS (bm25) ─┐
    └─► вектор ───┴─► RRF ─► priority ─► [реранк] ─┬─ max_chars
                                                    ├─ per_topic
                                                    ├─ dedup
                                                    └─ budget
```

## Канал 1: FTS5

`facts_fts` — обычный FTS5 с `unicode61 remove_diacritics 2`, то есть ё и е
считаются одной буквой.

```python
def _fts_match(q):
    toks = _WORD.findall(q)[:12]
    return " OR ".join('"' + t.replace('"', '""') + '"' for t in toks)
```

**OR, не AND.** Первые версии склеивали слова через `AND`, и запрос «микрот firewall
порт» находил ровно ноль записей, хотя все три слова в базе есть. OR даёт широкую
воронку, а лишнее отсекается на ранжировании. Ограничение — 12 слов: длинный
вопрос не должен превращаться в 200 кандидатов.

Вклад в итоговый счёт: `fts_w / (60 + rank)`. 60 — константа RRF: она прижимает
разницу между первым и вторым местом, чтобы один канал не диктовал порядок.

## Канал 2: вектор

`bge-m3` (1024 измерения, `llama-server --embeddings` на :8081), косинус в
`sqlite-vec`:

```python
hits = con.execute(
    "SELECT fact_id, distance FROM fact_vec "
    "WHERE embedding MATCH ? AND k = ? ORDER BY distance",
    (struct.pack(f"{len(vec)}f", *vec), limit * 2))
```

Вклад: `vec_w / (60 + rank)`. Если эмбеддер недоступен, `_embed` возвращает `None`
и поиск идёт на одном FTS — сервис не падает, просто отвечает лексикой.

## Слияние: RRF, взвешенный приоритетом

```python
score = rrf * (0.5 + priority / 100)
```

- `priority`: `constraint` 75, `decision` 70, `settings` 65, `fact` 60, `skill` 40,
  `chat` 30, `pinned` 100.
- Множитель 0.5–1.5: важное всплывает, но **не переворачивает релевантность**.
  Запись с priority 100 и слабым сходством не обгонит точное совпадение с 60.

Почему RRF, а не нормализация: bm25 (отрицательный, без верхней границы) и cosine
(0–1) несоизмеримы. Ранги соизмеримы всегда, и RRF не требует калибровки при
смене модели эмбеддингов.

### Веса каналов

`fts_w=0.3, vec_w=1.0` по умолчанию. Равные веса (1.0/1.0) — измеренная ошибка:
FTS заливает топ длинными чанками, где слово запроса встречается один раз на сотню
других. Замеры на 12 запросах — `docs/benchmarks.md`.

Чувствительность больше зависит от базы, чем от константы: на базе, где половина
записей — чанки скилов по 700 символов, лексика шумит сильнее.

## Ограничители выдачи

Режут не кандидатов, а уже отсортированный список.

| Ограничитель | По умолчанию | Зачем |
|---|---|---|
| `max_chars` | 250 | обрезка по границе слова; чанк в 700 символов съедал половину бюджета и вытеснял остальное |
| `per_topic` | 2 | десяток кусков одного разговора в выдаче бесполезен |
| `dedup` | Jaccard основ ≥ 0.72 | две почти одинаковые записи — это одна запись |
| `budget` | 800 токенов | `_tokens(text) = len/3.2` |

Ограничители **мягкие**: если с ними не набралось `limit`, второй проход добирает
остаток без лимита на тему. Иначе на узкой теме выдача была бы всегда неполной.

Обрезка живёт только в выдаче — в базе текст целый. Это важно: `max_chars=250`
не портит данные, поэтому значение можно менять под задачу.

### Основы слов, а не слова

`_stems()` — грубая нормализация для дедупа и хука:

```
сопла / сопло / соплом  → сопл
P104 / V100 / PF450     → целиком (код)
PCIe / PETG             → целиком (латиница)
```

Правило: слово от 5 символов режется до 4; слово от 3 символов сохраняется целиком,
если в нём есть цифра или оно латинское. Стоп-слова (`какой`, `можно`, `что`,
`about`, …) выбрасываются — иначе запрос «какой порт у WebDAV» совпадал бы с любой
записью про порты.

Четыре символа, а не пять: пять не ловило падежи (`сопла` vs `сопло`), шесть — тем
более. Цена — редкие ложные склейки, лечится тем, что склейка работает только
внутри одного `kind` и только при Jaccard ≥ 0.9.

## Реранк: есть, но выключен

`rerank=true` отправляет top-N (по умолчанию 12) в `bge-reranker-v2-m3` на :8083.

Измерено на этой базе: включение **ухудшает** MRR (0.771 → 0.729) и добавляет
~1.5 с. Причина: реранк переставляет только top-12, а промахи рождаются раньше —
нужный факт может стоять в FTS на 177-м месте (запрос «дедупликация», факт «dedup»
— разные основы). Реранк лечит порядок, а проблема в отборе.

Поэтому он остался параметром для экспериментов, а не частью горячего пути.

## Свежесть и штраф чату: выключены

- `recency_w=0` — буст по `created_at` не меняет MRR: свежие записи в базе в
  основном чанки чатов, и буст тянет мусор.
- `chat_w=1.0` — штраф `kind=chat` (0.6) роняет MRR и шум не убирает: чат несёт
  настоящую историю решений, а не только трёп.

Оба параметра остались в API: конфигураций много, дефолт выбран замерами.

## Хук: почему фильтр по основам, а не по скору

`/recall_hook` не может себе позволить «отдай что-нибудь». Он вставляет текст в
каждый ход, поэтому молчание лучше мусора.

RRF-скоры лежат в узкой полосе: один канал ~0.016, оба ~0.032, фоновый шум тоже
0.016. Порог по скору отсекает мусор вместе с правильными ответами. Решает
**пересечение основ** слов запроса и текста факта:

```python
overlap = len(q_stems & _stems(item["text"] + " " + item["topic"]))
if overlap == 0 or item["score"] < min_score:  # выбросить
    continue
rank_key = item["score"] + stem_boost * overlap
```

На боевой базе: 9 из 12 целевых запросов дотягивают нужный факт до промпта, 3 из 3
посторонних дают пустой ответ. Средний блок — 466 символов (~145 токенов),
средняя задержка 205 мс. Промахи — там, где запрос и факт не делят ни одной основы
(«камера принтера стрим» против записи про `ustreamer`).

### Почему блок режется построчно

`per_line = max_chars // limit`. Раньше лимит считался по сумме строк, и при
`max_chars=700` и записи в 500 символов в промпт попадала ровно одна строка вместо
четырёх. Теперь при `limit=4, max_chars=900` каждая строка ~225 символов, и нужный
факт доходит чаще (на контрольном наборе 11/12 против 9/12 при старом счёте).

## Диагностика: две пары запросов

Вопрос «почему не нашлось» решается за две команды.

```bash
# 1. Есть ли вообще такое в базе (без поиска)
sqlite3 context.db "select count(*) from facts where text like '%p104%'"

# 2. Кто виноват: канал или слияние
curl -sG localhost:8090/recall -H "X-Context-Token: $TOK" \
  --data-urlencode 'q=дедупликация памяти' --data 'fts_w=0&vec_w=1'   # только вектор
curl -sG localhost:8090/recall -H "X-Context-Token: $TOK" \
  --data-urlencode 'q=дедупликация памяти' --data 'fts_w=1&vec_w=0'   # только FTS
```

Симптомы, с которыми уже сталкивались:

| Симптом | Причина | Что делать |
|---|---|---|
| кандидатов много (`dropped.cands` > 20), `items` мало | `max_chars` × `per_topic` × `budget` срезали | поднять `budget`/`limit` |
| нужный факт на 8-м месте, чисто векторный поиск ставит на 1-е | вес FTS завышен | `fts_w=0.3` |
| поиск молчит на перефразе, но находит по точному слову | эмбеддер недоступен | `/health`: `vectors:false` → `/reindex` |
| «нашлось 5 записей», а нужной нет | все 5 — куски одного разговора | `per_topic=2`, `dedup=true` |
| хук молчит, а `/recall` отдаёт | нет пересечения основ | смотреть `_stems(q)` |

## Что не делать

- Не «улучшать» FTS через `AND`: широкий OR плюс ограничители работает лучше.
- Не включать реранк «для качества»: на этой архитектуре он замедляет и портит.
- Не мерить качество числом записей в выдаче. Метрика — **попал ли нужный факт**,
  с заранее заданной подстрокой. Набор и методика: `docs/benchmarks.md`.
- Не подбирать `max_chars`/`per_topic` на глаз: они взаимодействуют, нужна сетка
  при реальном `budget`.
