# Наполнение: откуда в памяти берутся записи

Сервис сам по себе пустой — он умеет только хранить и искать. Наполняют его четыре
источника, и у каждого свой характер шума.

| Источник | Что кладёт | `topic` | `kind` | Объём на боевой базе |
|---|---|---|---|---|
| Рука | решения, настройки, ограничения | свободный | `fact` / `decision` / `constraint` / `settings` | 218 записей |
| `skills_index.py` | файлы скилов агента, чанки 700 символов | `skill/<имя>` | `skill` | 5 870 чанков, 89 тем |
| `sessions_index.py` | история чатов агента, окна диалога | `chat/<YYYY-MM>` | `chat` | 3 124 чанка |
| `ctxagent` | Nextcloud, `inbox/*.md|txt|json` | `nc/<путь>`, `inbox/<файл>` | `fact` | 6 записей |

Плюс `session_ingest.py` — разовый путь «транскрипт → 1–10 атомарных фактов» через
локальную модель.

## Индексатор скилов

```
~/AppData/Local/hermes/skills/            каталог = ближайший предок с SKILL.md
~/.config/opencode/skills/
   ├── *.md, *.txt, *.py, *.sh, *.yaml  → чанки по секциям, ~700 символов
   ├── пропуск: assets, templates, outputs, node_modules, .git, .venv
   └── topic = skill/<имя>, kind = skill, префикс чанка «[скил · файл]»
```

- **Инкрементальность**: `skills_index.state.json` хранит хеш файла и id его чанков.
  Хеш не изменился — файл пропускается (повторный прогон — 0 с). Изменился —
  старые чанки удаляются через `DELETE /forget?id=`, новые заливаются.
- **Почему 700 символов, а не 900**: эмбеддер принимает максимум 512 токенов, а
  плотный код/hex-цвета дают до 0.6 символа на токен. Чанк 900 символов иногда
  падал с `input (N tokens) is too large`. Плюс `push_items()` режет текст пополам
  при такой ошибке.
- **Частично залитый файл не попадает в state** — следующий прогон его повторит.
  Ошибки пишутся в `skills_index.err.log`.
- Первичный прогон на 353 файлах — ~25 минут (bge-m3 на CPU, ~5.3 текста/с).

## Индексатор истории чатов

Читает SQLite агента (`state.db`) в режиме `mode=ro`, берёт `role in ('user','assistant')`,
склеивает диалог и режет на чанки.

```
сессия → «U: …» / «A: …» → чанки → /remember_bulk
topic = chat/<YYYY-MM>, kind = chat, source = chat-index, tags = <id сессии>
```

Фильтры, которые пришлось ввести:

- сообщения короче 40 символов — мимо («да», «ок», «продолжай»);
- служебные префиксы — мимо (`[IMPORTANT:`, `[CONTEXT COMPACTION`, `[OUT-OF-BAND`,
  `[INTERNAL NOTIFICATION`, `[SYSTEM:`, `[Background process`, `Память contextd`);
- сессия обрезается на 200 КБ;
- прогресс пишется в `sessions_index.state.json` после каждой сессии — обрыв
  прогона не теряет работу.

Секреты режутся регуляркой (см. `docs/writing.md`, раздел «Секреты»), но правило
«ключевое слово вплотную к значению» оставляет дыру: одиночный пароль в сообщении
проходит фильтр.

Чат — самая шумная часть базы: 3 124 чанка против 218 ручных записей. Именно
поэтому ему дали `priority=30` и штраф `chat_w`, а не наоборот.

## ctxagent: внешние источники

Отдельный сервис на :8091 (вне этого репозитория, но часть той же памяти):

- коннектор Nextcloud: WebDAV PROPFIND по заданным путям, `.md/.txt`, чанки ~1100
  символов, тема `nc/<путь>`, хеш файла в `state.json`;
- коннектор `inbox`: `~/ctxagent/inbox/*.md|txt|json` → разбор → `inbox/done/`;
- фоновый цикл раз в 180 минут, cron не нужен;
- `_redact()` перед записью: пары `password|пароль|token|токен|secret|api key: <значение>`,
  `curl -u ...`, строки из 28+ символов `[A-Za-z0-9_-]`, hex 20+.

`_redact()` отключать нельзя: файл-карта сервера в Nextcloud содержит app-пароль,
токен доступа и пароль БД — без фильтра они уехали в память (проверено, вычищено).

## session_ingest: транскрипт → факты

```
session_ingest.py --once            # обработать inbox (по таймеру)
session_ingest.py --file PATH       # один файл
session_ingest.py --stdin           # из stdin
session_ingest.py --once --dry-run  # показать, что легло бы
```

Просит у локальной модели (OpenAI-совместимый `/v1/chat/completions`) только
долговечное, до 10 фактов, до 200 символов каждый. Без модели падает в
консервативный построчный фильтр — сервис памяти не должен зависеть от того,
поднята ли генерация.

## Порядок наполнения, если начинаешь с нуля

1. `remember` 10–20 ручных фактов, которые реально нужны каждый день.
2. Закрепить 3–5 из них (`/pin`) — они пойдут в `/context` всегда.
3. Подключить хук и пожить неделю: пустая память в хуке не мешает, а покажет,
   каких запросов не хватает.
4. Прогнать индексатор скилов (он даёт самый предсказуемый прирост).
5. Только потом историю чатов: она даёт объём, но и шум.

## Грабли индексаторов

- **Два индексатора в одну тему воюют**: перед своим — посмотреть, что уже
  залито (`select topic, count(*) from facts group by 1`).
- **Удаление по id из state должно идти до вставки новых чанков**, иначе `/forget`
  может снести только что добавленные.
- **Не индексировать `outputs/`, `templates/`, `assets/`**: это копии и мусор,
  поиск по ним даёт ложные попадания.
- **Хеш файла, а не mtime**: правка конфига с сохранением mtime (git checkout)
  иначе не переиндексируется.
- Счётчик фактов **плавает между замерами** — индексаторы перед перезаливкой зовут
  `/forget` по старым чанкам. Снимать два замера с интервалом, а не искать баг по
  одному числу.
